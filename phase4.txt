Phase 4 — Advanced Website Builder

Goal:
Turn the visual editor from a portfolio-specific page editor into a powerful but controlled personal website builder.

Phase 3 lets students visually arrange components. Phase 4 gives them more control over behavior, layout, pages, animations, and richer content while still protecting them from breaking their website.

The guiding principle remains:

More creative freedom, without turning the product into an unrestricted code editor.

1. Multiple Pages

Students can now create more than one page.

For example:

My Website

├── Home
├── About
├── Projects
├── Resume
└── Contact

Each page gets a clean URL:

/crystal
/crystal/about
/crystal/projects
/crystal/resume
/crystal/contact

The student can create, rename, reorder, and delete pages.

2. Navigation Builder

Students can visually manage their navigation.

Example:

Navigation

Home
About
Projects
Resume
Contact

Add a page

Reorder links

Link to external websites
Link to sections
Link to another portfolio page

The navigation component automatically updates.

3. Advanced Layout System

Phase 3 provides predefined layouts.

Phase 4 introduces more flexible layout controls.

Students can control:

Rows
Width
Maximum width
Alignment
Gap

Margins

Responsive behavior

┌───────────────────────────────┐

│                               │
└───────────────────────────────┘

The student can adjust the relationship between the columns without needing to understand CSS Grid or Flexbox.

4. Responsive Rules

The builder should become smarter about responsive design.

A component can have different settings for:

Desktop
Tablet
Mobile

For example:

Desktop
3 project columns
Tablet
2 project columns
Mobile
1 project column

The user controls the important behavior while the platform handles the underlying responsive implementation.

For example, a button can have:

Focus
Disabled

Each website can have a polished fallback page.

Example:

19. Custom Cursor / Decorative Effects

I'd actually avoid exposing this initially.

It's tempting to add:

Custom cursors
Mouse-following effects
Particle effects
Background blobs
Excessive parallax

But these are exactly the kinds of things that can turn a professional portfolio into visual clutter.

If we eventually add them, they should be carefully curated components—not arbitrary effects.

20. Version History

This becomes increasingly important as websites become complex.

Students should eventually be able to see:

Versions

Today
  9:42 PM — Current

Today
  8:17 PM — Added Projects section

Yesterday
  6:32 PM — Changed homepage design

Yesterday
  4:10 PM — Initial version

And restore an earlier version.

This protects users from accidentally destroying their design.

21. Draft / Published Versions

By this point, the distinction should be very clear:

                 Website
                    │
        ┌───────────┴───────────┐
        │                       │
      Draft                  Published
        │                       │
     Editing                 Visitors
        │
     Preview
        │
     Publish

The public website should never show half-finished changes.

22. Performance

This phase introduces much more complexity, so performance becomes a major requirement.

Public portfolios should:

Load quickly
Optimize images
Avoid unnecessary JavaScript
Avoid huge bundles
Lazy-load media
Use responsive images
Minimize unnecessary requests

A student portfolio should not feel like a heavy web application to its visitors.

23. Accessibility

Every new component must remain accessible.

For example:

Modals need proper focus management
Tabs need keyboard navigation
Accordions need accessible controls
Images need alt text
Buttons need proper labels
Animations need reduced-motion support
Color contrast must remain acceptable

Accessibility isn't something we add later.

24. MySQL Plan

Continue with:

MySQL + Prisma

The website configuration becomes increasingly structured.

Conceptually:

Website
│
├── Theme
├── Pages
│    ├── Page
│    │    ├── Sections
│    │    │    └── Components
│    │    │         ├── Properties
│    │    │         └── Actions
│    │    └── SEO
│    │
│    └── ...
│
└── Versions

We should be careful about database design here.

The goal is to support complex editing without making every tiny UI change require dozens of relational database operations.

A structured document/configuration approach may make sense for the page builder, while core student data remains relational.

25. Vercel Plan

Continue using Vercel as the application deployment platform.

Development:

Next.js
   ↓
Prisma
   ↓
Local MySQL

Production:

GitHub
   ↓
Vercel
   ↓
Next.js
   ↓
Prisma
   ↓
Hosted MySQL

We continue to prioritize free-tier infrastructure during development and early validation.

As the platform gains users, we'll evaluate paid infrastructure based on actual usage rather than paying for unnecessary capacity upfront.

26. PWA

The editor/dashboard should now feel like a proper installable application.

Students should be able to:

Install it
Open it like an app
Edit their portfolio
Manage drafts
Preview their website

However, the public portfolio remains a normal web experience.

27. What Phase 4 Does NOT Include

Still avoid:

❌ Arbitrary JavaScript
❌ Arbitrary HTML
❌ Full custom CSS
❌ Code editor
❌ Plugin marketplace
❌ Third-party extensions
❌ Real-time collaboration
❌ Team editing
❌ Custom domains
❌ Payments
❌ University administration

Those belong to later phases.
