Phase 3 — Visual Portfolio Editor

Goal:
Transform the portfolio builder from a template/customization system into a controlled Canva-like website editor.

The student should now be able to visually build and rearrange their portfolio instead of only changing predefined template options.

The key principle:

Give students creative freedom without giving them the ability to accidentally break their website.

8. The Button Problem

This is one of the most important parts of Phase 3.

Users must not write JavaScript to define what a button does.

Instead:

Button Action
Action:

○ Open URL
○ Open project
○ Scroll to section
○ Send email
○ Download file
○ Open social profile

The application handles the actual implementation.

9. Smart Actions

Some actions should understand the student's portfolio.

For example:

Button

View my GitHub

Action:

Social Link → GitHub

The system automatically gets the GitHub URL from the student's profile.

If they change their GitHub URL later, the button automatically uses the new URL.

This is much better than storing a hardcoded URL inside every button.

10. Internal Page Navigation

Students should be able to create navigation such as:

About
Projects
Experience
Contact

The editor understands these as sections.

So:

Contact

can automatically scroll to:

#contact

The student doesn't need to understand anchors.

11. Undo / Redo

A visual editor absolutely needs:

Undo

Redo

Students will make mistakes constantly.

The editor should support a history of changes.

For example:

Add image
 ↓
Move image
 ↓
Resize image
 ↓
Change color
 ↓
Undo
 ↓
Undo

The website returns to its previous state.

12. Duplicate

Every major component should support:

Duplicate

For example:

Project Card
      ↓
Duplicate
      ↓
Project Card 2

This makes creating portfolios much faster.

13. Delete

Selected components can be deleted.

For destructive operations, provide appropriate confirmation when necessary.

For example:

Delete this section?

Cancel | Delete

But don't annoy users with confirmation dialogs for every tiny action.

14. Keyboard Shortcuts

The editor should eventually support familiar shortcuts:

Ctrl/Cmd + Z     Undo
Ctrl/Cmd + Shift + Z   Redo
Ctrl/Cmd + C     Copy
Ctrl/Cmd + V     Paste
Delete           Delete element

This makes the editor feel much more professional.

17. Mobile Safety

The editor should actively prevent broken layouts.

For example:

If the user creates:

5 columns

the system should not blindly reproduce that on a phone.

Instead:

Desktop
5 columns

Mobile
1 column

The platform should prioritize usable websites over absolute design freedom.

18. Images

Students should be able to:

Upload images
Replace images
Crop images
Set aspect ratio
Add alt text
Reposition/crop the visual

But image uploads need proper validation and security.

We should also think about image optimization because portfolio websites need to load quickly.

19. Component Data Binding

This is one of the most important architectural concepts.

A component should be able to reference the student's actual data.

For example:

Project Grid
       ↓
Student's Projects

If the student adds another project:

Database
   ↓
Projects
   ↓
Project Grid automatically updates

They shouldn't have to manually edit the website every time they add a project.

20. Example: Project Component

The student adds:

Projects

The component dynamically renders the student's actual project data.

This is what separates our builder from a generic design editor.

21. Design System

The visual editor should continue using the Phase 2 design system.

Components inherit:

Colors
Typography
Spacing
Border styles
Button styles

Students can override certain properties when appropriate.

This prevents every component from becoming visually inconsistent.

23. Draft System

The editor should work with drafts.

Published Website
       │
       │
Student edits
       ↓
Draft
       │
       ├── Preview
       │
       └── Publish

Visitors should only see the published version.

This becomes extremely important as the editor gets more powerful.

24. Autosave

The editor should save changes automatically where practical.

For example:

Saved just now

or:

Saving...

Saved

But autosave should not replace the explicit Publish action.

Autosave = save the draft.

Publish = make it public.

25. Preview Mode

The student should be able to switch from:

Edit

to:

Preview

Preview should remove editing controls and show the portfolio almost exactly as a visitor would see it.

26. Public Renderer

This is a critical architecture rule.

The public portfolio should not simply render the editor UI.

Instead:

Editor
   ↓
Portfolio configuration
   ↓
Public renderer
   ↓
Visitor

The public website should be:

Fast
SEO-friendly
Accessible
Responsive
Lightweight

Visitors should never know that the website was built using a visual editor.

27. Security

The visual editor must never allow arbitrary code execution.

Do not allow users to save:

<script>
...
</script>

or arbitrary JavaScript.

User-generated content should be safely rendered.

The editor should operate through a controlled component system.

28. MySQL Plan

Continue using:

MySQL + Prisma

The database now needs to represent the student's website configuration.

Conceptually:

User
 │
 └── Website
      │
      ├── Theme
      ├── Pages
      ├── Sections
      ├── Components
      └── Component configuration

The important thing is that the database stores structured website data, not generated HTML.

For example:

Button
 ├── text
 ├── style
 └── action
      ├── type
      └── target

This makes the editor predictable and secure.

29. Vercel Plan

Continue using Vercel for the application.

Development:

Local Next.js
      ↓
Local MySQL

Production:

GitHub
   ↓
Vercel
   ↓
Next.js
   ↓
Hosted MySQL

We should continue targeting the free tier while validating the product.

30. PWA

The dashboard/editor should be installable as a PWA.

However, the public portfolio remains a normal web page.

The editor should prioritize desktop/tablet because complex visual editing is difficult on small screens.

31. What Phase 3 Does NOT Include

We're still not building:

❌ Arbitrary JavaScript
❌ Custom HTML
❌ Full Webflow-level CSS
❌ Infinite canvas
❌ Pixel-perfect absolute positioning everywhere
❌ Plugin marketplace
❌ Third-party app ecosystem
❌ Collaborative editing
❌ Advanced animations
❌ Custom domains
❌ Payments

Those are later considerations.
